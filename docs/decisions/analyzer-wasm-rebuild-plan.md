# Rebuilding the GoogleSQL analyzer for googlesqlite

Status: investigation, not carried out. This document records how the
analyzer wasm that googlesqlite embeds is produced and what a rebuild
with a newer upstream googlesql and extra bindings would involve. It
was written by reading the upstream repositories and their CI runs;
nothing was built. It is referenced from
[analyzer-default-time-zone.md](analyzer-default-time-zone.md).

## 1. Repo chain and how each artifact is produced

```
google/googlesql  (C++, bazel 7.6.1)
   | git submodule, pinned at 36dd14aa = tag 2026.01.1 (2026-01-30)
   v
goccy/googlesql-wasm   (wasmify.json + Makefile + .github/workflows/build.yml)
   | GitHub release vX.Y.Z assets, each with a SLSA attestation:
   |   googlesql.wasm (13.9 MB), googlesql_wasm2go.tar.gz (39 MB),
   |   googlesql_wasm2go.sha256, googlesql_wasm2go.go (11 MB), googlesql_wazero.go
   +--> goccy/googlesqlwasm2go  (v0.2.0 = wasm v0.3.4)
   |      `make bundle`: curl the tarball, check sha256, run `gh attestation verify`, commit the tree
   +--> goccy/go-googlesql      (v0.4.0)
          `make googlesql`: curl googlesql_wasm2go.go -> googlesql.go, verify the attestation
          go.mod: require github.com/goccy/googlesqlwasm2go v0.2.0
   v
goccy/googlesqlite (this driver): require go-googlesql v0.4.0, wasm2go v0.2.0 // indirect
```

Key facts:

- **All binding code is generated in googlesql-wasm.** Nothing is hand-written.
  `go-googlesql/googlesql.go` is marked "Code generated by protoc-gen-wasmify-go"
  and is just a downloaded release asset. The repo holds only that file plus
  tests. The C++ bridge (`bridge/api_bridge.cc`), `api-spec.json` and the proto
  are also generated during the build and never committed.
- **You cannot regenerate the bindings "Go-side only".** `googlesql.go` calls
  numbered entry points such as `wasm2go.Inv_554_68`. The bridge's
  service/method numbering is fixed when the wasm is built. Any new binding
  therefore needs a new wasm build, and the `googlesql.go` and wasm2go bundle
  from that same build must ship together.
- **Generator:** `goccy/wasmify` (CLI + protoc-gen-wasmify-go), run from the
  container image `ghcr.io/goccy/wasmify:v0.4.8`. The latest wasmify release is
  v0.6.17 (2026-09-10), so the pin is several minors behind.
- **The build is controlled by `wasmify.json`.** It holds the upstream commit
  and `bridge.ExportFunctions`, `ExternalTypes`, `SkipHeaders`,
  `OwnershipTransferMethods` and so on. It also embeds the Go import paths
  `GoPackage: github.com/goccy/go-googlesql` and
  `Wasm2GoImportPath: github.com/goccy/googlesqlwasm2go`.
- **Build pipeline** (inside the container, `make wasm`, same steps as CI):
  `wasmify build` -> `generate-build` -> `parse-headers` -> `gen-proto` ->
  `wasm-build --optimize` -> `buf generate --timeout 30m` -> `make bundle-gomod`.

### Existing CI: GitHub Actions already does the heavy build

`googlesql-wasm/.github/workflows/build.yml` runs on push to main, `v*` tags,
PRs and `workflow_dispatch`:

- It runs on `ubuntu-latest` (4 vCPU, 16 GB RAM, about 4 GB swap). A
  free-disk-space step first raises free disk to about 41 GB.
- It reuses a warm cache image, `ghcr.io/<owner>/googlesql-wasm-cache:<wasmify-tag>-<submodule-sha>`.
  On a cache miss (and only on push events) it `docker commit`s and pushes a
  new cache image.
- It uploads the artifacts, adds a build-provenance attestation, and publishes
  the release assets when a tag is pushed.
- Past run times: a cold build (for example after a wasmify bump) took about
  2 to 3.5 h. A warm tag build (v0.3.4) took about 35 min. Both fit within the
  6 h job limit.

The two downstream repos each have a light `ci.yml`: attestation verify plus
`go build`.

### Resource needs (do NOT run locally)

- The Makefile gives the container `MEMORY=14g`, `CPUS=8`.
- The comments say the C++ compile and link peak at about 6 GB.
- The wasm2go code generation (40k functions, 3.2M SSA instructions) was
  OOM-killed on a 16 GB runner when swap was disabled.
- A cold build downloads a multi-GB LLVM toolchain and needs more than 14 GB
  of disk.

**Conclusion:** this exceeds a typical developer workstation (a local
attempt can freeze the machine). Run the build only on GitHub Actions. Locally, only download the release assets and `go build`/`go test`
the driver (which already compiles the 11 MB `googlesql.go`).

## 2. The three needs

### Need 1: UTC default time zone

**Current state.** `absl::TimeZone` is listed in `ExternalTypes`, so the Go
`TimeZone` is an opaque handle with no constructor. The only exported ways to
get one are:

- `AnalyzerOptions.DefaultTimeZone()`, which returns a borrowed pointer to
  `data_->default_timezone`.
- `SetDefaultTimeZone(*TimeZone)`.

The upstream constructor hard-codes the default:
`FindTimeZoneByName("America/Los_Angeles")` (`analyzer_options.cc:328`).

**Escape hatches that are not bound.** The proto path
(`AnalyzerOptionsProto.default_timezone` plus `AnalyzerOptions::Deserialize`)
would also do it, but none of it is usable from Go:

- `AnalyzerOptions::Deserialize` has no binding.
- The proto message exposes no string setter; `SetAllocatedDefaultTimezone`
  was generated with a broken signature.

`absl::UTCTimeZone` / `FixedTimeZone` / `LoadTimeZone` and
`googlesql::functions::MakeTimeZone` are not exported either. The only
TimeZone symbols in the wasm are cctz internals.

The options, cheapest first:

- **(a) Go only, no rebuild. A deliberate memory poke; it needs checking before use.**
  - `absl::TimeZone` is a `cctz::time_zone`, which is one pointer (4 bytes on
    wasm32).
  - A null `impl_` means UTC. This is how `cctz::utc_time_zone()` and a
    default-constructed `absl::TimeZone` work.
  - `opts.DefaultTimeZone()` gives the address of the options' own TimeZone.
    Writing 4 zero bytes at that address in `base.Module.Memory` turns it into
    UTC.
  - `Memory` is exported in `googlesqlwasm2go/base`. The module handle is
    internal to go-googlesql, so the helper, for example
    `func (h *AnalyzerOptions) SetDefaultTimeZoneUTC() error`, must live in our
    go-googlesql fork, in a small hand-written file next to the generated one.
  - Checks before relying on it:
    - Confirm that handle values are raw linear-memory addresses.
    - Confirm the absl layout by reading back the old value (non-zero) first.
    - Test it: analyze `SELECT CAST('2020-01-01 00:00:00' AS TIMESTAMP)` with
      folding on and assert the UTC micros.
  - Fragile, but zero C++ work, and it removes the TIMESTAMP folding
    workaround in the driver today.
- **(b) Clean fix: bridge config plus a rebuild.** Expose a function that
  returns a TimeZone. Two ways:
  - Add a tiny public helper to the upstream googlesql tree (needs a googlesql
    fork or a patch step in the build), for example
    `absl::TimeZone googlesql::UTCTimeZoneForBridge()` or a string-taking
    `AnalyzerOptions::SetDefaultTimeZoneByName`. List it in `ExportFunctions`.
  - Or try adding `absl::UTCTimeZone` / `googlesql::functions::MakeTimeZone`
    directly. This probably won't work: absl is an external dependency and is
    not header-parsed, and `MakeTimeZone` uses an out-parameter of an opaque
    type.
  - Either way it goes in the same rebuild as need 2, so it costs nothing extra.

### Need 2: newer upstream googlesql

- **Current version.** The submodule and `wasmify.json` point to `36dd14aa`,
  which is exactly tag **2026.01.1**.
- **Pipe AGGREGATE fixes.** `pipe_aggregate_mixed_expression` (line 294) and
  `pipe_aggregate_correlated_subquery` (line 302) are absent from
  `compliance/testdata/pipe_operators.test` at 2026.01.1. They are present in
  **2026.7.2**, 2026.9.1 and 2026.9.2.
- **MATCH_RECOGNIZE nesting error.** The message "MATCH_RECOGNIZE clause
  cannot be nested inside another MATCH_RECOGNIZE clause" is at
  `resolver_query.cc:13365/13563` and in `analyzer/testdata/match_recognize.test`
  at 2026.01.1. It is gone from the testdata at 2026.7.2 and later.
- **Build tool.** `.bazelversion` is 7.6.1 in all of these tags, so there is no
  bazel jump.
- **Target.** Upgrade to **2026.9.2**, the latest (2026-09-16). This is a
  submodule plus `wasmify.json upstream.commit` change, followed by a cold
  rebuild on CI.
- **Layer.** Upstream version bump plus rebuild. No bridge changes, but new
  headers may need `SkipHeaders`/`ExternalTypes` tweaks if the build fails.

### Need 3: collation bugs

- **`NewSimpleColumn2` drops the annotation and crashes.**
  - On the Go side, `AnnotatedType.marshal()` does send the `AnnotationMap`
    handle, so the loss happens in the generated C++ bridge. That is either how
    the by-value `AnnotatedType{const Type*, const AnnotationMap*}` struct is
    rebuilt, or ownership.
  - `SimpleColumn` stores a raw `const AnnotationMap*` that must outlive it,
    which normally means it is owned by a `TypeFactory`.
  - There is also no exported way to create an `AnnotationMap`:
    `AnnotationMap::Create` returns `unique_ptr` and is not bound.
    `TypeFactory.TakeOwnership` and `AnnotationMap.SetAnnotation` exist.
  - **Layer:** the wasmify generator (goccy/wasmify, a fourth repo) and/or
    `wasmify.json`, for example an `OwnershipTransferMethods` entry, exporting
    `AnnotationMap::Create`/`StructAnnotationMap`, or wiring through
    `TypeFactory::TakeOwnership`. All of these need a rebuild.
  - **First step:** rebuild with wasmify v0.6.17. It may already fix
    struct-with-pointer marshalling. Read the generated `bridge/api_bridge.cc`
    in the CI artifact or cache image, not locally.
  - **Go-only workaround to try meanwhile:** analyze a
    `CREATE TABLE t (c STRING COLLATE 'und:ci')` statement and reuse the
    analyzer-owned `AnnotatedType`. The analyzer output must be kept alive.
- **Templated SQL UDF returning `COLLATE(...)` fails type inference.** This is
  analyzer semantics in upstream C++, not the binding. First retest after the
  2026.9.2 bump. If it still fails, the fix is either a patch to the googlesql
  resolver (needs a Flip-to googlesql fork or a patch step in the wasm build)
  or a driver-side workaround.

| Need | Minimal change | Layer |
|---|---|---|
| UTC time zone | (a) memory-poke helper in the go-googlesql fork, or (b) export a TimeZone-returning function | (a) Go only; (b) bridge config/C++ shim plus rebuild |
| Pipe AGGREGATE, MATCH_RECOGNIZE | googlesql 2026.01.1 -> 2026.9.2 | upstream bump plus rebuild |
| NewSimpleColumn2 collation | wasmify bump and/or ownership/export config | generator/bridge plus rebuild |
| UDF COLLATE inference | retest after bump; else patch the resolver | upstream C++ (maybe) |

## 3. Recommended plan

1. **Fork `goccy/googlesql-wasm` into Flip-to.**
   - Keep it **public**. The workflow attests only when the repo is public, and
     the downstream `verify` targets require attestations.
   - Enable Actions on the fork, since forks start with Actions disabled.
   - Allow `GITHUB_TOKEN` to write packages for `ghcr.io/flip-to/googlesql-wasm-cache`
     (org package settings). The first run is cold, about 3 h.
   - A fork of `goccy/wasmify` is only needed if the generator itself needs
     patching (need 3).
2. **Make the changes in the googlesql-wasm fork, on a branch, and open a PR to
   run CI.**
   - Bump the `googlesql` submodule to tag 2026.9.2 (`0e7d7073…` is 2026.7.2;
     resolve 2026.9.2's SHA). Update `wasmify.json.upstream.commit`.
   - Optionally bump `WASMIFY_IMAGE` (workflow) and `IMAGE` (Makefile) to
     v0.6.17. Do it in the same cold build, but expect churn in the generated
     API.
   - Add the need-1(b) export and the need-3 config.
   - **Keep `GoPackage`/`Wasm2GoImportPath` at the goccy paths.** The bundle
     embeds the path in `//go:linkname`, so renaming it would force renaming
     both downstream modules. `replace` handles the fork instead.
   - Merge, then push tag `v0.3.5-flipto.1` (or similar). CI publishes the
     release assets.
3. **In the `Flip-to/googlesqlwasm2go` fork:**
   `make bundle GOOGLESQL_WASM_REPO=Flip-to/googlesql-wasm GOOGLESQL_WASM_VERSION=<tag> GOOGLESQL_WASM_WORKFLOW=Flip-to/googlesql-wasm/.github/workflows/build.yml`.
   - Update the Makefile defaults to those values.
   - Commit and tag, for example `v0.2.1-flipto.1`.
   - This is download plus extract only, so it is light, or it can be done in
     a CI job.
4. **In the `Flip-to/go-googlesql` fork:** `make googlesql` with the same
   three variables (light).
   - Point the Makefile defaults at the Flip-to repo. They currently say
     v0.3.1 and are stale.
   - Add the hand-written helper file (need 1(a)), plus tests.
   - Set `go.mod require github.com/goccy/googlesqlwasm2go <fork tag>`.
   - Tag, for example `v0.4.1-flipto.1`.
5. **In googlesqlite:** set `go.mod` as below. `replace` directives in
   go-googlesql's own go.mod are ignored by consumers, so both replaces must be
   in the driver.
   ```
   replace (
       github.com/goccy/go-googlesql      => github.com/Flip-to/go-googlesql      v0.4.1-flipto.1
       github.com/goccy/googlesqlwasm2go  => github.com/Flip-to/googlesqlwasm2go  v0.2.1-flipto.1
   )
   ```
   - The fork go.mod files must keep `module github.com/goccy/...`.
   - Note: `replace` does not carry over to downstream consumers of the
     driver. If external users must get the fixes, they need the same replaces,
     or the forks must be renamed to Flip-to module paths (which would mean
     changing `GoPackage`/`Wasm2GoImportPath` and rebuilding).
   - Then drop the TIMESTAMP folding workaround and re-enable the
     pipe/MATCH_RECOGNIZE/collation compliance cases.
   - Run tests with capped parallelism (`go test -p 1`). Run `bench/`
     against `bench/RESULTS.md`.
6. **Optional:** send the upstream-able pieces (version bump, TimeZone export,
   collation fix) as PRs to goccy so the forks can eventually be dropped.

## 4. Risks

- **Generated API churn.**
  - Upgrading googlesql by about 8 months and/or wasmify from 0.4.8 to 0.6.17
    can rename or renumber generated symbols. The `NewSimpleColumn2`-style
    overload suffixes depend on declaration order.
  - It can also change method signatures the driver uses. Expect a
    compile-fix pass in `internal/`.
  - Doing the googlesql bump alone first (keeping wasmify 0.4.8) limits the
    changes.
- **Behaviour changes in the new analyzer.** New error messages and resolved
  AST shapes can break existing testdata expectations. Per CLAUDE.md, fix the
  implementation, never the testdata.
- **CI capacity.** A cold build takes about 3 h on a 16 GB runner, and wasm2go
  code generation has OOM'd before without swap. The v0.4.6 runs failed on
  2026-07-09. A failed build costs a multi-hour retry. A PR run cannot seed the
  cache (push-only), so the first push-to-main after merging is cold again.
  Budget for two cold builds.
- **Attestations.** If the fork is private or the attest step fails,
  `make verify` in both downstream repos fails. Keep the fork public.
- **Need 1(a) memory poke.**
  - It depends on the absl/cctz layout and on handles being raw addresses.
  - Each new `AnalyzerOptions` must be poked.
  - If upstream ever copies options internally before `CHECK`ing the time
    zone, the poke still survives, because a copy duplicates the pointer, and
    null means UTC.
  - Treat it as a stopgap until 1(b).
- **Performance.** A larger or newer analyzer may change analysis time. Run the
  `bench/` suite against the baseline before release.
- **Module-path replace.** It works for this repo only. Consumers of
  googlesqlite do not inherit it (see step 5).
